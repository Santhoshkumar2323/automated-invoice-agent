# Invoice Agent

A scheduled pipeline that reads GST invoices with AI, checks them against compliance rules, and enters only the valid ones into an accounting system. It runs on GitHub Actions and reports to a public dashboard.

**[Open the live dashboard](https://automated-invoice-agent-sk.streamlit.app/)** 

(Note if the page is asleep, give it a minute to wake up)

> All data is synthetic. The invoices, vendors, tax registry and "accounting system" are fake, and are generated by this project.

## What it does

Every few hours the pipeline:

1. Generates one or two realistic Indian GST tax invoices as PDFs. About one in four contains a deliberate problem (a wrong total, a bad GSTIN checksum, a suspended vendor, a duplicate, and so on).
2. Reads each PDF with LlamaParse, which turns the page layout into Markdown.
3. Asks an LLM (Groq, `openai/gpt-oss-20b`) to turn that Markdown into structured fields.
4. Runs compliance checks written as ordinary code.
5. If every check passes, a browser robot types the invoice into a small accounting website and confirms the entry.
6. Saves a report, a screenshot and the token usage, then updates the dashboard.

Because the planted problems are known in advance, every run also scores itself: did the system make the right decision, and were the extracted fields correct?

A cloud run takes about two to three minutes.

## How it works

```text
Scheduler: switched on? run due? inside the time window? budget left?
  -> Pre-check: is the accounting website running?
  -> Generate PDFs (some with a planted problem) and a hidden answer key
  -> For each PDF:
       LlamaParse: PDF -> Markdown
       Groq: Markdown -> invoice fields
       Checks: schema, GSTIN format/checksum/state, arithmetic,
               tax type, duplicate, vendor registry status
         all pass                      -> robot enters it, confirms, screenshots = ACCEPTED
         vendor problem or duplicate   -> stopped, no retry                      = REJECTED
         could be a misread            -> ask the model again with the errors
                                          (at most 2 times)
         invoice itself is wrong, or the retry changes nothing                   = NEEDS_REVIEW
         technical failure = ERROR       daily budget used up = SKIPPED
  -> Report, usage log, cleanup of old files
```

| Status | Meaning |
|---|---|
| ACCEPTED | All checks passed, the robot entered it, and the website confirmed it |
| VALIDATED | Passed all checks in a dry run (no ledger entry) |
| REJECTED | A policy problem: suspended, revoked or unknown vendor, or a duplicate |
| NEEDS_REVIEW | A number or GSTIN is wrong and a retry cannot fix it, so a person should look |
| ERROR | A technical failure (API, parser or browser) |
| SKIPPED | The daily budget ran out first |

## Where AI is used, and where it is not

- **AI:** LlamaParse reads the page layout. The Groq model extracts the fields from the text.
- **Plain code:** every check, every accept or reject decision, the retry rules and the browser robot.
- No AI decides whether an invoice goes into the ledger.
- When a check fails in a way that could be a misread, the model is asked again with the list of errors, up to two times. The retry is skipped when the invoice itself prints the failing numbers, or when the model returns the same answer on the retry, because another call would only cost tokens.
- The browser step is scripted automation that finds form fields by their labels. It is not an AI choosing where to click.


## Results

As of 7 October 2026, from the three cloud runs recorded in this repository (`python -m src.summary --full-only`):

| Measure | Result |
|---|---|
| Runs and invoices | 3 runs, 6 invoices |
| Outcomes | 4 accepted, 1 rejected, 1 needs review |
| Extraction accuracy | 100% (66 of 66 fields) |
| Planted problems caught | 2 of 2 |
| Clean invoices wrongly stopped | 0 of 4 |
| Tokens per invoice | about 1,900, with no retries so far |
| LlamaParse pages | 6 (one per invoice) |
| Cost | runs on free tiers |

Earlier local testing, before deployment (23 invoices; those reports are not kept in this repository): all 14 planted problems were stopped, all 9 clean invoices were accepted, and 253 of 253 fields were correct.

Treat these as a working demonstration, not a benchmark. The sample is small, and the invoices come from the same generator that was used to write the checks. The 446 automated tests (`pytest`) use fake AI and browser services and run offline.

## Safety and cost controls

- Daily token and page budgets, with a master on/off switch and an optional time window.
- Retries are capped, and skipped when they cannot help.
- The pipeline checks that the accounting website is running before it spends anything.
- The accounting website enforces its own rules (duplicates, GSTIN format and checksum), so a bad invoice that slipped past the pipeline would still be refused there.
- The ledger file is never overwritten if it is damaged, and it is written so a crash cannot leave a half-written file.
- API keys live in GitHub Secrets only. A test scans the repository files for anything that looks like a key.
- Old screenshots, reports and logs are deleted automatically according to limits in `config.yaml`.

To stop the cloud runs: on GitHub choose Actions, then `pipeline`, then **Disable workflow**. You can also set `pipeline.enabled: false`, or open a time window with `python -m src.window --hours 5`.

## Tech

Python 3.13, LangGraph, Pydantic, LlamaParse (`llama-cloud`), the Groq API, Playwright, Streamlit, ReportLab, GitHub Actions, LangSmith (optional tracing) and pytest.

## Run it yourself

<details>
<summary>Setup and commands</summary>

You need Python 3.13 and free accounts at Groq and LlamaCloud. LangSmith is optional.

```powershell
git clone https://github.com/Santhoshkumar2323/automated-invoice-agent
py -3.13 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
playwright install chromium
```

Create a file named `.env` in the project folder with your keys (never commit it; it is ignored by Git):

```text
GROQ_API_KEY=your_key
LLAMA_CLOUD_API_KEY=your_key
LANGSMITH_API_KEY=optional
```

Then:

```powershell
pytest                                   # the tests, no keys needed
streamlit run app/ledger_app.py          # terminal 1: the accounting website
python -m src.main --force --count 2 --defect NONE --show-browser   # terminal 2: a full run
streamlit run app/monitor_app.py --server.port 8502                 # terminal 3: the dashboard
python -m src.summary --full-only        # the scoreboard
```

Each invoice uses about 1,900 tokens and one parsed page. Free-tier limits apply, and model names can change: if the default model is no longer offered, change `llm.model` in `config.yaml`.

To run it on your own GitHub account, publish the code, add the secrets `GROQ_API_KEY`, `LLAMA_CLOUD_API_KEY` and (optionally) `LANGSMITH_API_KEY` under Settings, Secrets and variables, Actions, and run the `pipeline` workflow once by hand.

</details>

## Configuration

Every setting is in `config.yaml` and is checked when the program starts.

| Setting | Default | Meaning |
|---|---|---|
| `pipeline.interval_hours` | 3 | Hours between runs |
| `pipeline.invoices_per_run` | 2 | Invoices per run |
| `pipeline.bad_invoice_ratio` | 0.25 | Share of invoices with a planted problem |
| `pipeline.max_retries` | 2 | Repair attempts per invoice |
| `pipeline.run_until` | empty | Stop automatic runs after this time |
| `budget.daily_token_limit` | 100000 | Tokens per UTC day |
| `budget.daily_page_limit` | 50 | Parsed pages per UTC day |
| `llm.model` | `openai/gpt-oss-20b` | The Groq model |
| `retention.max_screenshots` | 40 | Newest screenshots kept |

## Limitations

- All data is synthetic, and the PDFs use one invoice layout. A 100% score here says nothing certain about real invoices.
- The GSTIN checks use the published format and check-digit rule. The vendor registry is a small fake list, not the government's. The tax rate is fixed at 18%.
- The sample so far is small.
- GitHub's scheduler is best-effort. Scheduled runs started less often than hourly, with one gap of about 12 hours.
- The "accounting system" is a small web page backed by a JSON file, not a real ERP.
- Free-tier services change their limits and models. The default Groq model had to be replaced once during development.
